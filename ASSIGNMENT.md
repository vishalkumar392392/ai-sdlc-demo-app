## The feature

| Invoice amount | Who can approve | Result |
| --- | --- | --- |
| ≤ 50,000.00 | one Manager or one Director | Approved |
| 50,000.01 – 500,000.00 | one Director | Approved |
| > 500,000.00 | two **distinct** approvers; the **second** must be a Director | 1st approval: still PendingApproval ("1 of 2 approvals"); 2nd: Approved |

A refused attempt returns **HTTP 403 `{ "error": "<reason>" }`**. The reason names the role, the limit and what is needed. **Nothing about the invoice changes**, and nothing is saved.

### Does the context file matter?

AGENTS.md and the `approval-rules` skill name the specific traps. The implementer sub-agent was asked to read them and implement step 2. On the first attempt it:

- read recorded approvals, not `DecidedBy`
- compared usernames trimmed and case-insensitively
- validated fully before mutating

It also proved each of these with a deliberate break. Before this change, the original AGENTS.md said none of this: no limits, no "nothing changes" rule, no `ApprovalPolicy`. A cold agent would have had to guess.

For the video, a side-by-side run is suggested: the same step-2 prompt in a fresh session with the old AGENTS.md vs the new one. I did not run that controlled A/B here.

| Concurrency (review F1) | `ApprovalServiceConcurrencyTests`: two Directors at once; approve racing a decline |

**Every generated test was reviewed against "what would turn it red?".** Each rule was broken on purpose and at least one test failed every time:

- mutate before the check
- `>` → `>=` at both limits
- drop the same-user check
- `==` instead of case-insensitive comparison
- trim without ignoring case, and vice versa
- append the approval before the check
- drop Director-second
- make the first approval final
- remove the decision lock (5 of 5 runs red)

**Playwright** (`cd e2e && npm test`): `tests/approval-limits.spec.ts`. demo.manager creates and submits a 50,000.01 invoice and clicks Approve. The test asserts:

- the response is **403**
- the alert says "Manager approval limit is 50,000.00 … needs a Director"
- the invoice is still pending in both views

It uses page objects with `getByRole`/`getByLabel` only. I verified it fails when `ManagerLimit` is raised to 60,000.

## Decisions and deviations (worth knowing)

1. **Roles.** `Approver` is replaced by `Manager` and `Director`. New demo users are `demo.manager`, `demo.director`, `demo.director2` and `demo.admin`, all with password `ChangeMe123!`. Admin can still decline but **cannot approve** (separation of duties).
2. **Limits are inclusive.** 50,000.00 is within a Manager's limit.
3. **Above 500,000, the first approver may be a Manager.** That is the literal reading of "the second approver must be a director". It is recorded as an open question in `design.md`.
4. **E2E port 5080** (`E2E_PORT` overrides it). On macOS, AirPlay Receiver owns :5000, and Playwright's `reuseExistingServer` silently tested against it.
5. **Seed data** adds INV-1006 (72,500) and INV-1007 (640,000) as pending invoices for live demos.

## How to run

```bash
# .NET 8 SDK (installed here to ~/.dotnet)
export DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$HOME/.dotnet/tools:$PATH

dotnet test backend/InvoiceApp.sln                                  # unit tests

cd e2e && npm install && npx playwright install chromium && npm test # e2e
cd backend/tests/InvoiceApp.Tests && dotnet stryker                  # mutation (dotnet-stryker 4.13.0)
```
